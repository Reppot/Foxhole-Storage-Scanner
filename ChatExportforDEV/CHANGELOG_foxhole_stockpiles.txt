====================================================================
ОТЧЁТ ПО ПРОЕКТУ: Foxhole Stockpiles -> Discord Relay
====================================================================
Экспорт переписки/изменений для передачи программисту.
Формат: TXT. Дата экспорта в чате не хранится системой — указывайте
актуальную дату сами при передаче.

--------------------------------------------------------------------
1. ЗАДАЧА В ЦЕЛОМ
--------------------------------------------------------------------
Приложение FS (Foxhole Stockpiles) сканирует склады в игре Foxhole
(через OCR-скриншоты или через парсинг .sav-файла сохранения) и
может отправлять результат на произвольный webhook (JSON POST).

Discord API ожидает СВОЙ формат тела запроса (поля content/embeds),
а FS шлёт "сырой" JSON со списком предметов склада. Поэтому напрямую
подключить вебхук FS к вебхуку Discord нельзя — нужен посредник
(relay), который:
  1) принимает сырой JSON от FS,
  2) переводит коды предметов на русский и подбирает иконки,
  3) форматирует всё в Discord embed,
  4) пересылает в реальный Discord-вебхук.

--------------------------------------------------------------------
2. ХРОНОЛОГИЯ РАБОТ (кратко, в порядке выполнения)
--------------------------------------------------------------------

2.1. Диагностика исходной проблемы с вебхуком
    - Пользователь пытался подключить сырой Discord webhook URL прямо
      в качестве "URL вебхука" в FS.
    - Причина неработоспособности: тело запроса FS не соответствует
      схеме Discord (нет полей content/embeds) -> Discord отвечает
      ошибкой и ничего не публикует.
    - ВАЖНО (безопасность): пользователь несколько раз публиковал в
      чате свой реальный Discord webhook URL (включая токен). Токен
      был помечен как скомпрометированный, пользователю рекомендовано
      пересоздать вебхук в Discord (Настройки сервера -> Интеграции ->
      Вебхуки -> Удаление/пересоздание). Программисту: перед деплоем
      убедиться, что в проде используется НОВЫЙ, не засвеченный токен,
      заданный только через переменную окружения, а не в коде/чате.

2.2. Создание relay.py (Flask-сервер)
    - Python + Flask. Слушает POST на /relay.
    - Принимает JSON от FS (одиночный объект стоkpile ИЛИ обёртку
      {"stockpiles": [...]}).
    - Фильтрует пустые сканы (SKIP_EMPTY_SCANS, по умолчанию True) —
      если все предметы с quantity=0, сообщение в Discord не шлётся.
    - Формирует Discord embed(ы) (до 10 за раз, ограничение Discord).
    - Пересылает на реальный DISCORD_WEBHOOK_URL (переменная
      окружения, не хардкодить в коде).
    - Есть /health для диагностики (виден ли ICONS_DIR, сколько
      иконок проиндексировано, задан ли DISCORD_WEBHOOK_URL).
    - Запуск: `python relay.py`, порт по умолчанию 5001
      (переменная RELAY_PORT).
    - Зависимости: flask, requests (requirements.txt).

2.3. Проблемы окружения на машине пользователя (Windows)
    - Python был установлен через "Python install manager" (Microsoft
      Store-стиль), из-за чего алиасы `python`/`py` в cmd не работали
      сразу после установки.
    - Решение: Параметры Windows -> Приложения -> Дополнительные
      параметры приложений -> Псевдонимы выполнения приложения ->
      включить/выключить-включить "Python (default)" и "Python install
      manager" (python.exe и py.exe).
    - `pip` как отдельная команда не был зарегистрирован — использовать
      `python -m pip install -r requirements.txt` вместо голого `pip`.

2.4. Источник данных: OCR vs .sav
    - Изначально FS сканировал склад через OCR скриншота — оказалось,
      что распознавание количества и особенно ТИПА предметов (особенно
      техники/транспорта) сильно ошибается.
    - Переключились на режим SAV (Обработка SAV -> Мониторинг (авто)),
      который читает данные из локального файла сохранения игры и
      даёт точные значения (без угадывания по пикселям).
    - Важный нюанс: SAV-режим показывает только ЗАКРЕПЛЁННЫЕ (pinned)
      в игре склады.
    - Файл сохранения по факту не "MapData.sav", как предполагалось
      изначально, а создаётся/находится самим FS через
      "Автоопределение" в настройках (путь у пользователя:
      %LOCALAPPDATA%\Foxhole\Saved\SaveGames\<SteamID>_MapData.sav —
      именно "_MapData"-версия, НЕ путать с обычным
      "<SteamID>.sav", который является файлом настроек ИГРОКА
      (PlayerSaveGame), а не данными карты/складов).
    - Для отладки на стороне ассистента использовалась сторонняя
      Python-библиотека `fs-sav` (PyPI) — парсер .sav в JSON.
      Полезно для программиста, если понадобится независимая
      проверка содержимого сохранения.

2.5. Формат сообщения в Discord (финальный, по запросу пользователя)
    Заголовок сообщения (в начале description embed'а):
        **Гекс:** <название региона>
        **Регион:** <ТИП СКЛАДА ЗАГЛАВНЫМИ> (например "ПОРТ")
        **Склад:** <имя склада или "—">
    Далее список предметов:
        • **<Название по-русски>** — <кол-во> (в ящике)
    Поля embed'а снизу: Шард, Разрешение (может быть "—", если нет
    данных, напр. для SAV-сканов).
    Название региона (hex) берётся из поля "hex" в данных SAV
    (например "ClansheadValleyHex" -> "Clanshead Valley" —
    убирается суффикс "Hex" и разбивается CamelCase на слова).
    Короткие коды типа склада: Seaport->"ПОРТ",
    Storage Depot->"СКЛАД", Facility->"ОБЪЕКТ",
    Small Facility->"МАЛЫЙ ОБЪЕКТ", Field->"ПОЛЕВОЙ СКЛАД".

2.6. Перевод названий предметов (ITEM_NAMES_RU в relay.py)
    - FS присылает "код" предмета (например "AluminumA",
      "TruckDefensiveW") — не готовое название.
    - Собран вручную словарь ITEM_NAMES_RU: код -> русское название,
      подтверждённый напрямую пользователем (по игровым тултипам).
      На момент последнего файла relay.py — около 100+ записей.
    - Для кодов без перевода в словаре есть автоматический fallback
      prettify_code(): разбивает CamelCase на слова ("MetalBeam
      Materials" вместо голого кода) — чтобы не было совсем нечитаемо,
      пока перевод не добавлен вручную.
    - Отдельный, более масштабный источник переводов — файл
      item_codes.py (см. п. 2.8) с ~477 записями (ITEM_CODES),
      сгенерированными полуавтоматически из имён файлов-иконок и
      автороитетных списков (vehicle_names.txt и т.п.), которые
      пользователь предоставлял отдельно от игры/сайта.
      ITEM_NAMES_RU и ITEM_CODES на момент экспорта — это ДВА разных
      словаря, не до конца объединённых между собой; ITEM_NAMES_RU
      имеет приоритет там, где есть explicit-запись, ITEM_CODES —
      более широкий довесок. Программисту стоит решить, объединять ли
      их в единый источник правды или оставить раздельно.

2.7. Иконки предметов в Discord-сообщении (относительно новая фича)
    - Изначально relay.py отправлял только текстовый embed.
    - Позже добавлена возможность прикладывать иконку предмета
      (судя по структуре текущего relay.py — там появились функции
      build_icon_index() / find_icon_path(), значит embed теперь
      умеет ссылаться на локальный файл иконки).
    - Иконки пользователь собирал вручную из внутриигровых
      скриншотов инвентаря (много итераций нарезки скриншотов сетки
      предметов на отдельные PNG, см. п. 3).
    - Каталог иконок был организован пользователем самостоятельно
      (внешний инструмент/сайт) в папке:
        D:\Games\foxhole-stockpiles-main\Foxhole-Storage\Icons Foxhole
      Внутри — 9 РАЗНЫХ подпапок (в т.ч. вложенные
      All\Storage\Unnamed\1\Icons, ...\11\Icons3 и др.) ИЛИ файлы прямо
      в корне. Всего на момент последней ревизии — 597 файлов
      (по списку icons_list.txt, из них 582 реально изображения,
      остальное — служебные txt/csv и сами директории, попавшие в
      листинг).
    - Корневая папка дополнительно содержит отдельный "каталог
      техники" — 117 файлов с числовым префиксом (001_Barge.png …
      117_Atlas.png), это отдельный набор коротких названий техники/
      транспорта, добавленный в item_codes.py как ~115 новых записей
      (2 уже существовали под другими именами).
    - Авторитетный источник точных названий для этих 117 — файл
      vehicle_names.txt, присланный пользователем отдельно (формат
      "NNN Название"). Из него названия и коды сгенерированы ЗАНОВО
      (первая попытка генерации из имён файлов была ОШИБОЧНОЙ: терялись
      апострофы (O'Brien) и "/" заменялся на "-" в составных названиях
      типа "Strider 30/12.7x2" — это баг был найден пользователем и
      исправлен).

2.8. ИТЕКУЩАЯ АРХИТЕКТУРА ПОИСКА ИКОНОК В relay.py (важно для
     программиста, т.к. это последнее и наименее стабилизированное
     изменение)
    - ICONS_DIR (env var ICONS_DIR, дефолт — путь из п. 2.7, корень
      "Icons Foxhole").
    - build_icon_index(): РЕКУРСИВНО (os.walk) сканирует ICONS_DIR и
      все подпапки, строит словарь нормализованное_имя -> путь.
      Кэшируется в processe (_icon_index_cache) — считается один раз
      за время жизни процесса.
    - Для файлов с числовым префиксом ("001_Barge.png") индексируются
      ОБА варианта ключа: с префиксом и без него ("001barge" и
      "barge") — чтобы обычные короткие FS-коды типа "Barge" тоже
      находили файл.
    - _normalize(): нормализация — вероятно приведение к нижнему
      регистру и вырезание всего, кроме [a-zа-я0-9] (нужно свериться
      с актуальным кодом файла, т.к. эта функция не менялась в
      последних правках, но именно от неё зависит, совпадут ли ключи).
    - ITEM_ICON_FILES: словарь EXPLICIT-переопределений код -> имя
      файла иконки, для случаев, когда автоматический подбор не
      сработал бы (например разные FS-коды для одной и той же техники:
      AmbulanceFlameW и MediumBoatC оба -> Salva.png, потому что это
      один и тот же реальный объект под двумя историческими кодами).
    - find_icon_path(code, display_name):
        1. Если code есть в ITEM_ICON_FILES — ищет ПУТЬ ЭТОГО ФАЙЛА
           ЧЕРЕЗ ИНДЕКС (build_icon_index), а не склейкой пути
           напрямую — это принципиальное исправление, внесённое ПОСЛЕ
           того, как ICONS_DIR сменили с узкой подпапки на общий
           корень (при прямой склейке пути вложенные иконки бы не
           находились).
        2. Иначе — пробует несколько кандидатов (code как есть,
           "причёсанный" code, display_name) через нормализованный
           поиск в индексе; плюс fuzzy-сравнение (difflib) с порогом
           отсечения ~0.85 для "почти совпадающих" имён.
    - unmapped_items.log: relay пишет туда JSON-строки по каждому
      предмету, который НЕ удалось сопоставить с иконкой и/или
      названием (name_missing / icon_missing флаги) — это основной
      диагностический инструмент для донастройки словарей.

--------------------------------------------------------------------
3. ОТДЕЛЬНАЯ ПОБОЧНАЯ ЗАДАЧА: нарезка скриншотов инвентаря на иконки
--------------------------------------------------------------------
Пользователь несколько раз присылал скриншоты сетки иконок предметов
(8 колонок x N строк) из внутриигрового UI склада/каталога, просил
нарезать на отдельные PNG и подписать по списку названий.
Это было сделано НЕСКОЛЬКО раз с итерациями (проблема дублей между
скриншотами при скролле, проблема рассинхрона порядка список<->сетка,
в итоге договорились до порядка "картинки по номерам 1->6, внутри
каждой — слева направо по строкам"). Результат этой работы, судя по
всему, лёг в основу папки Icons Foxhole (см. п. 2.7) — то есть эта
задача НЕ отдельная, а подготовительный этап для базы иконок relay.py.
Программисту эта секция интересна только для понимания, откуда взялся
корпус иконок, самого кода она не касается.

4. ИЗВЕСТНЫЕ ОТКРЫТЫЕ ВОПРОСЫ / НЕЗАВЕРШЁННОЕ (на момент экспорта)
--------------------------------------------------------------------
- ГЛАВНОЕ: последний присланный пользователем unmapped_items.log
  показывает icon_missing=true АБСОЛЮТНО ДЛЯ ВСЕХ предметов, включая
  такие, для которых explicit-путь в ITEM_ICON_FILES точно существует
  и раньше работал. Это выглядит как "пустой индекс" (ICONS_DIR не
  находится на диске в момент запуска relay, либо путь отличается от
  ожидаемого, либо пользователь ещё не подставил обновлённые
  relay.py/item_codes.py и не перезапустил процесс).
  Диагностика запрошена, но ответ от пользователя ещё не получен:
    1) Подтвердить, что оба файла (relay.py и item_codes.py)
       заменены и relay перезапущен (Ctrl+C, заново `python relay.py`).
    2) Открыть http://127.0.0.1:5001/health и свериться, что
       icons_dir существует и число проиндексированных файлов > 0.
  Программисту следующим шагом нужно разобрать ответ /health, как
  только пользователь его пришлёт, и либо поправить путь ICONS_DIR,
  либо поискать причину пустого индекса в build_icon_index().

- ITEM_NAMES_RU (relay.py) и ITEM_CODES (item_codes.py) — два разных,
  не до конца согласованных словаря. Стоит рассмотреть объединение.

- Много кодов техники/аммуниции (ArmoredCar2TwinW, TrailerLiquid,
  TrailerResource, MediumBoatW, ATRPGAmmo, MiniTankAmmo, ATGrenadeW,
  LightTankAmmo, SatchelChargeW, WaterBucket, GasMaskFilter,
  FacilityMaterials1/4, LargeFieldMultiW и др.) до сих пор помечены
  name_missing=true в логе — ни явного русского названия, ни
  сопоставленной иконки. Часть из них была БЕЗ подтверждения от
  пользователя (см. закомментированные "???" в ITEM_ICON_FILES).

--------------------------------------------------------------------
5. ФАЙЛЫ ПРОЕКТА (актуальные версии на момент экспорта)
--------------------------------------------------------------------
- relay.py           — Flask-сервер посредник FS -> Discord.
- item_codes.py       — вспомогательный словарь код->название
                         (~477 записей), импортируется в relay.py.
- requirements.txt    — flask, requests.
- unmapped_items.log  — лог-файл, который relay.py сам ведёт в
                         рабочей папке рядом с собой (не входит в
                         репозиторий, генерируется в рантайме).

Все текстовые правки в этом экспорте описаны по памяти переписки;
перед тем как опираться на конкретные номера строк/названия функций,
сверьтесь с актуальным содержимым relay.py и item_codes.py — часть
формулировок в этом документе (особенно нормализация имён и точный
список ключей ITEM_NAMES_RU) приведена по смыслу, а не дословной
выпиской кода.

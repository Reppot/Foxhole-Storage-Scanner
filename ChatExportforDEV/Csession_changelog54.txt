--------------------------------------------------------------------
0. КОНТЕКСТ ПРОЕКТА
--------------------------------------------------------------------
Проект: relay.py — Flask-приложение, которое принимает POST от
Foxhole Stockpiles (FS) на /relay и пересылает содержимое склада
в Discord через webhook.

Данные о предмете приходят с полем "code" (внутренний идентификатор
предмета). Задача relay.py — превратить code в человекочитаемое
русское название (ITEM_NAMES_RU) и подобрать иконку (ITEM_ICON_FILES
+ автопоиск по ICONS_DIR).

В процессе сессии выяснилось, что у проекта ДВА независимых
источника данных о предметах:
  (а) "боевой" webhook от FS с реальными внутренними code
      (пример: "AluminumA", "LiquidContainer") — так работали
      исходные ~250 записей в ITEM_NAMES_RU/ITEM_ICON_FILES.
  (б) экспорт через игровую кнопку "Copy to Clipboard" — отдаёт
      только текстовые названия предметов, БЕЗ внутреннего code.
      Для этого пути в проекте есть отдельный сгенерированный модуль
      item_codes.py: ITEM_CODES = {синтетический_code: имя_предмета},
      где synthetic code — это транслитерация самого имени предмета.
      relay.py подгружает его так:
          for _code, _name in ITEM_CODES.items():
              ITEM_NAMES_RU.setdefault(_code, _name)
      То есть ручные записи в ITEM_NAMES_RU имеют приоритет, а всё,
      что не переопределено вручную, добавляется автоматически из
      item_codes.py. Оба набора кодов мирно сосуществуют как разные
      ключи одного словаря.

1. РЕНДЕР СКЛАДА В КАРТИНКУ (пагинация на несколько Discord-сообщений)
--------------------------------------------------------------------
Проблема: у пользователя уже была функция render_stockpile_image(),
рисующая ОДНУ картинку на весь список предметов склада (иконка +
название + количество, фон gray-background.jpg). Для крупных складов
(100+ позиций) картинка получалась в несколько тысяч пикселей высотой
— нечитаемо, плохо отображается в Discord/на мобильных.

Решение:
  - render_stockpile_image() -> render_stockpile_images()
    (мн. число). Теперь режет список предметов по
    MAX_ROWS_PER_IMAGE (по умолчанию 12) и возвращает СПИСОК PNG
    (список страниц), а не один байтовый объект.
  - Каждая страница дублирует шапку склада (Гекс / Тип / Склад) и
    добавляет бейдж "Стр. X/Y" в правый верхний угол (только если
    страниц больше одной).
  - Endpoint /relay переписан: раньше все embeds/файлы одного
    запроса паковались в ОДНО сообщение в Discord (до 10 attachments
    по лимиту Discord). Теперь каждая страница КАЖДОГО склада уходит
    ОТДЕЛЬНЫМ сообщением через новую функцию
    _send_single_image_message(), с паузой DISCORD_SEND_DELAY (по
    умолчанию 0.4 сек) между отправками, чтобы не словить рейт-лимит
    вебхука Discord (~5 запросов / 2 сек).
  - Новые переменные окружения:
        MAX_ROWS_PER_IMAGE=12
        DISCORD_SEND_DELAY=0.4

Попутно найдены и исправлены 2 бага вёрстки при тестировании:
  - Заголовок "Гекс: ... Тип: ..." на одной строке пересекался с
    бейджем "Стр. X/Y" при длинных значениях (например
    "МАЛЫЙ ОБЪЕКТ"). Исправлено: шапка разбита на 3 отдельные строки
    (Гекс / Тип / Склад), бейдж страницы — отдельной строкой в углу,
    коллизий больше нет ни при каких длинах строк.
  - Длинные названия предметов (например "12.7 мм (пулемётные)
    патроны") вылезали за правый край картинки. Добавлена функция
    _wrap_to_width() — перенос на строки по факту помещающейся
    ширины (до 2 строк, дальше — обрезка с многоточием), с
    вертикальным центрированием текста в границах ROW_HEIGHT.
  - Также добавлен fallback-список шрифтов (_FALLBACK_FONTS /
    _FALLBACK_FONTS_BOLD) на случай, если основной FONT_PATH/
    FONT_BOLD_PATH (обычно arial.ttf на Windows) не найдётся —
    иначе Pillow молча скатывается в ImageFont.load_default(),
    который не умеет кириллицу вообще (превращает весь русский
    текст в "тофу"-прямоугольники).

2. РАЗБОР .sav ФАЙЛА (PlayerMapDataSaveGame) И ВОПРОС "СРОК ДЕЙСТВИЯ"
--------------------------------------------------------------------
Пользователь просил выяснить, можно ли достать из локального save-
файла игры (*_MapData.sav, формат Unreal Engine GVAS) две вещи:
  (1) привязку координат склада к названию города/POI;
  (2) таймер "Срок действия" (когда истекает Reserve Stockpile).

Разбор бинарного формата (вручную, по спецификации GVAS: имя
свойства -> тип -> длина -> значение) показал:
  - Файл — это НЕ карта мира, а личный кэш игрока "закреплённых на
    карте тултипов" (PinnedMapToolTipSaveData). Содержит:
      MapId (enum EWorldConquestMapId, например "ClansheadValleyHex")
      NormalizedMapCoords (Vector2D, x/y от 0.0 до 1.0 внутри гекса)
      InitalMapItemDetails / RecentMapItemDetails (содержимое склада)
      LastUpdated (FDateTime, тики по 100нс с 0001-01-01) — момент,
        когда клиент локально закэшировал этот тултип, НЕ таймер
        распада.
  - Городов/POI в файле НЕТ вообще — только гекс + нормализованные
    координаты внутри него. Для привязки к городу нужен отдельный
    справочник координат POI по гексам, которого в файле нет.
  - Параметра "Срок действия" (expiration/decay) в файле НЕТ ни в
    каком виде. Проверены все поля структуры (Flags, DetailValue,
    AltDetailValue — везде константы/нули), выписан полный список
    уникальных имён свойств во всём файле — ничего похожего на
    timer/decay/expire/remaining нет.

Вывод: "Срок действия" — это значение, которое сервер FS считает "на
лету" и отдаёт клиенту в момент открытия окна склада; локально оно
нигде не кэшируется. Единственный легальный способ его получить —
OCR со скриншота (как и остальные текстовые поля в проекте). Прямой
перехват сетевого трафика клиент-сервер для этого НЕ рекомендован —
это нарушает ToS/анти-чит Foxhole и слишком хрупко (ломается каждым
патчем).

Статус: эта задача (научить сканер распознавать строку "Срок
действия: XXdXXh" через OCR) ОТЛОЖЕНА по просьбе пользователя,
исходный код сканера (stockpile_scanner) мне не передавался — нужен
для реализации.

3. ИЗВЛЕЧЕНИЕ ИКОНОК ИЗ СКРИНШОТА (категория "Сооружения")
--------------------------------------------------------------------
Пользователь прислал скриншот сетки предметов категории "Сооружения"
(8 колонок x 4 строки = 31 непустая ячейка). Задача: нарезать на
отдельные иконки 66x68 и подписать именами.

Метод нарезки: сетка на скриншоте была расшифрована программно —
поиск тёмных разделительных линий по яркости пикселей (искали
столбцы/строки со средней яркостью < 25) дал точные границы 8
колонок x 4 строк, дальше — обычный PIL crop + resize(66, 68).

Проблема: у 17 из 31 иконок на скриншоте НЕТ подписи текстом вообще
(видна только картинка). Программист был предупреждён об этом СРАЗУ
(до отправки архива), как и было явно запрошено в задании — вместо
того чтобы придумывать названия наугад. Доставлен zip с иконками:
для 12 позиций — уверенные названия по видимому тексту на картинке,
для 2 — названия с пометкой "неточно/неразборчиво", 17 — как
"unknown_NN.png" с контрольным листом (contact sheet) для сверки по
номерам.

Пользователь прислал txt с полными настоящими названиями всех 31
позиций (после сверки со своим игровым клиентом/каталогом).

4. МАППИНГ 31 ИКОНКИ НА КОДЫ (ДВЕ ИТЕРАЦИИ — важно для истории)
--------------------------------------------------------------------
ИТЕРАЦИЯ 1 (устарела, впоследствии отменена):
  Изначально у нас не было доступа к item_codes.py, поэтому для 27
  из 31 предмета (кроме 4 уже существующих контейнеров) коды были
  ПРИДУМАНЫ вручную в PascalCase-стиле (например "ConcreteMixer",
  "AOE9RocketBooster") — с явной пометкой в коде и в чате, что это
  ЗАГЛУШКИ, требующие подтверждения через unmapped_items.log.
  Имена файлов иконок при этом уже генерировались через транслит-
  функцию (см. ниже) и совпали 1-в-1 с уже существующими в проекте
  файлами (Zhidkostnyy Konteyner.png и т.д.) — это подтвердило, что
  схема транслитерации подобрана верно.

ИТЕРАЦИЯ 2 (ТЕКУЩЕЕ, актуальное состояние):
  Пользователь прислал реальный item_codes.py. Сверка показала: 30
  из 31 названий УЖЕ есть там с настоящими сгенерированными кодами
  (совпадение по точному тексту названия). Расхождения с моими
  заглушками из итерации 1:
    - "A0E-9 ..." (три предмета) — реальный код использует цифру
      "0" (ноль), а не букву "O": A0E9RaketnyyUskoritel,
      KorpusRaketyA0E9, A0E9RaketnayaBoegolovka.
    - "Huber Starbreaker 94.5" — полное игровое название на самом
      деле "Huber Starbreaker 94.5мм" (с "мм" в конце) => реальный
      код HuberStarbreaker94.5Mm.
    - "Huber Lariat 120мм" => код HuberLariat120Mm (заглавная "M").

  ИТОГ: все 27 ручных заглушек из ITEM_NAMES_RU и ITEM_ICON_FILES
  УДАЛЕНЫ из relay.py — они больше не нужны и были менее точными,
  чем автозагрузка из item_codes.py. Сейчас для всех 31 предметов
  перевод подтягивается автоматически через
  ITEM_CODES.setdefault(...), протестировано импортом вживую
  (import relay + реальный item_codes.py => все 31 названия
  резолвятся верно).

  Единственное, что осталось сделать вручную — положить файлы иконок
  в ICONS_DIR: раз имя файла точно равно коду (например
  "Betonomeshalka.png", "A0E9RaketnyyUskoritel.png"), find_icon_path()
  найдёт их автоматическим точным совпадением, без единой новой
  записи в ITEM_ICON_FILES.

Алгоритм транслитерации (используется и для проверки существующих
записей, и для генерации новых имён файлов), выведен реверс-
инжинирингом по уже существующим пар код/иконка в проекте:
  - Строка разбивается на токены по пробелам и дефисам.
  - Токен с кириллицей: транслитерируется посимвольно (таблица
    стандартная практическая: щ->shch, ц->ts, ч->ch, ш->sh, ж->zh,
    х->kh, ю->yu, я->ya, ъ/ь->'', ё->e), затем первая буква
    результата — заглавная, остальные строчные.
  - Токен без кириллицы (латиница/цифры, включая "DAE", "94.5",
    "AA-70") — не трогается, остаётся как есть.
  - Токены склеиваются без разделителей.
  - Пример: "Мешок с песком" -> "MeshokSPeskom" (предлог "с" тоже
    становится отдельным капитализированным токеном "S").
  Алгоритм проверен на 5 контрольных примерах из уже существующего
  словаря — совпадение 100%.
